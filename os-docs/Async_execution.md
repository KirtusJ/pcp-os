# What Rust and Tokio’s async history means for PCP

PCP has two distinct execution environments at source revision `0e068ee`. The hosted Rust program receives subagent lifecycle hooks and modifies a register under a transaction lock. The bare-metal x86_64 kernel schedules processes, takes interrupts and accounts for frames. Neither Rust build lists Tokio in its dependency graph. Asynchronous work is already observable in both environments. The relevant question for a change is what happens when a wake, stop, retry, or partial write arrives at the least convenient instant.

## Progress, load and clocks

Tokio’s 2019 scheduler rewrite used work stealing and wakeup changes to reduce overhead. In 2020 its maintainers described a different failure under load: a task can repeatedly await an operation that is always ready and never return control to the executor. A cooperative budget added opportunities to yield for supported Tokio resources. An arbitrary CPU loop, synchronous filesystem call or foreign library can still occupy the executor thread. For a PCP worker or UI, measure progress of a second runnable task and stop-request latency while the first is busy. For the kernel, measure actual timer/keyboard wakeups and frame ownership under load. Throughput or emulator test counts alone cannot answer those questions. [Tokio’s scheduler rewrite](https://tokio.rs/blog/2019-10-scheduler) · [Cooperative yielding under load](https://tokio.rs/blog/2020-04-preemption)

## Cancellation, drain and durable evidence

A Rust future can be dropped at a suspension point. In Tokio, dropping a spawned task’s join handle detaches the task. An abort request does not interrupt a blocking closure that is already running. In a `select!` loop, losing a race drops the unselected branch; restarting an operation with internal progress can lose that progress. For example, cancelling `write_all` can leave a prefix written. For a PCP register append or artifact publication, any async implementation needs an explicit owner for the commit and a recovery decision for a partially visible effect. A timeout, a stop request, worker exit and verification of result bytes are different observations. Keeping those distinctions lets a parent continue other work without promoting a missing result or declaring a live worker stopped. [Task join and detach](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html) · [Blocking work and shutdown](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html) · [Cancellation safety of select branches](https://docs.rs/tokio/latest/tokio/macro.select.html#cancellation-safety)

## Which failures occurred on PCP

Two simultaneous deliveries of one start hook created two open register tasks on the tested host. A single observed exit closed just one. Two distinct IDs sharing their first 200 characters also collapsed to the same stored attempt label. When the second worker finished first the host wrote its result against the first task. All those writes were serialized. A valid hash chain and exclusive lock preserve the written history; neither establishes that a completion was assigned to the right operation. The repair binds full session and agent identity before display clipping, suppresses duplicate live starts under the transaction lock and refuses ambiguous historical matches. Resuming an agent after an observed exit is still supported. The existing hook payload has no distinct generation counter for a resumed agent: a delayed stop from an old run carrying exactly the same identity as a new run would require stronger upstream evidence to disambiguate. [Host hook and transaction](../PCP_OS_Rust/crates/pcpos-host/src/pcpos.rs) · [Host integration tests](../PCP_OS_Rust/crates/pcpos-host/tests/host.rs)

The kernel has its own evidence. On the tests-only revision in PR #33 a stopped program still appeared running, and rejecting one program leaked 263 frames in the exercised case. The repaired revision passed those two controls in QEMU. A subsequent partial-group admission test found a separate leak involving resources acquired for earlier group members. Both cases illustrate why cancellation and startup failure need checks on the observable task state **and** the owned resources. The emulator findings apply to the tested machine configurations. [Kernel review and replay](https://github.com/KirtusJ/pcp-os/pull/33) · [Partial-group rollback fixture](https://github.com/KirtusJ/pcp-os/issues/35)

## Applying these lessons to an implementation

For a future hosted async path, identify who owns the attempt, its permits, its partial output and its join handle at each await. For bursty arrivals, bound in-flight work according to downstream capacity and record what happens to items already admitted during shutdown. Carry a lock across an await only when the protocol genuinely requires it and downstream work can progress without acquiring the same lock. Test a writer stopped before, during and after commit, concurrent duplicate starts, exit order reversed, a worker that never yields, and shutdown with an already-running blocking operation when the proposed implementation has those paths. Compare the final register, result bytes, active workers and resource use with the intended outcomes. Deterministic small-state interleaving tools such as Loom can check an isolated synchronization algorithm. OS-level hook, filesystem and interrupt tests exercise interactions outside that model. [Tokio shutdown guidance](https://tokio.rs/tokio/topics/shutdown) · [Loom model and limitations](https://docs.rs/loom/latest/loom/)
