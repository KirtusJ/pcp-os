# Build a tester CD from source

Nothing in this repository built a CD from the checked-out source: the tester images so far carry a kernel built elsewhere ([issue 288](https://github.com/KirtusJ/pcp-os/issues/288); the published kernel has since been rebuilt byte for byte from its historical source, see [the record](https://github.com/KirtusJ/pcp/pull/51#issuecomment-7056019582)). This directory is the recipe for the current source. It makes a BIOS optical image from the checkout and writes down what went into it. It publishes nothing: whether an image made this way is given to testers is a separate decision.

## What is on the CD and where each part comes from

| File | Source |
| --- | --- |
| `kernel.elf32` | `PCP_OS_Rust/crates/pcpos-kernel`, built by its own `run.sh build` with default features. Guest Ethernet is not compiled in. |
| `surf.elf` | `apps/surfbird/guest`, built with `--features local-media` |
| `clip.ppm`, `clip.wav` | generated by `apps/surfbird/guest/replay_local_media.py` (`make_media`, variant 0); the same bytes as on the published CD |
| `limine-bios.sys`, `limine-bios-cd.bin`, `limine.txt` | the Limine 10.8.5 binary release at commit `7a9013f305de0bea1f6310e76e7baba30499fef0`, each checked by SHA-256. This is the release whose BIOS path does not write to an attached disk ([disk check](../optical-disk-check/README.md)). |
| `limine.conf` | written by the builder; it names the measurement of the kernel that was just built |
| `notices.txt` | every external crate compiled into the kernel and included programs (reached through ordinary or build dependencies; crates used only by tests are left out), with the license files each crate ships |
| `boot.cat` | written by the mastering |
| `notice.md`, `readme.txt` | the workspace notice, and a short text naming the source commit and the measurement |

## Build

Linux, with Rust 1.97.0 including its source and the `x86_64-unknown-none` target, `ld.lld`, `objcopy`, `xorriso` and Python 3, and a checkout of the pinned Limine release:

```sh
rustup toolchain install 1.97.0 --profile minimal -c rust-src -t x86_64-unknown-none
git clone https://github.com/Limine-Bootloader/Limine limine
git -C limine checkout 7a9013f305de0bea1f6310e76e7baba30499fef0
python3 examples/tester-cd/build.py limine out
```

`out/pcp-os-tester.iso` is the image and `out/receipt.json` records the source commit and its tree (the tree identifies the files themselves, and stays checkable even if the commit is one a hosting service made for a test and later dropped), whether the checkout had uncommitted changes, the compiler, the features, the kernel's measurement and the size and SHA-256 of the image. It lists the files twice: `inputs`, the bytes handed to the mastering, and `on_disc`, the bytes read back from the finished image. The builder requires them equal for every file except the two the mastering writes: the boot catalog, and `limine-bios-cd.bin`, which receives its boot information table and so has a different digest on the disc (`925bf591…` for the pinned `913b56f2…`).

Only one build runs at a time in a staging folder; a second one started meanwhile stops with a message. The kernel is built from a private copy of the Rust workspace inside that folder, so nothing is written into the checkout. A different staging folder is a different build: it gives a different kernel measurement, so keep the default when two builds are meant to agree.

The image is assembled twice and the two must be equal. Both programs are compiled in one fixed folder (`/tmp/pcpos-tester-cd-build`, or `PCPOS_TESTER_CD_STAGE`), because the folder a crate is compiled in is part of what the compiler produces. With that, two builds of one commit into differently named output directories gave the same image on one machine. The folder the Rust toolchain is installed in still enters the kernel's measurement, so another machine can give another measurement and another image digest from the same commit. Compare receipts, and treat the digest of an image as belonging to the machine that built it until that is removed.

## Check

```sh
python3 examples/tester-cd/check.py out evidence
```

It boots the image with nothing but the CD attached on QEMU's `pc` and `q35` machines, each on the ordinary clock and on the instruction-counted one. In each of the four sessions the kernel must measure as the receipt says, pass exactly 71 startup self-tests and one more at power-off, play the demo to `DONE`, stop a second launch with the kernel's Stop key, and power off on request. The register screen is read cell by cell with the kernel's own font: it must say the chain is intact and show the two demo tasks ending DONE and STOPPED, with no cell that is not a character of the font. After Escape returns to the launcher, the checker verifies its startup status on screen, presses Escape again, reopens the register and requires the same task records. P explicitly powers off the guest. The Surfbird screen is saved. It fails if the kernel reports that guest Ethernet is compiled in. Run against the published CD it fails for that reason in all four sessions, which is the control for that assertion.

## Optional queue desk

To build a CD with two selectable applications, add `--queue-desk` to the build command. This builds the native Parrots queue desk and its dependencies from the same checkout and adds `rdesk.elf` to the Limine module list. Surfbird remains the first selection. The build receipt includes the on-disc ELF digest and the combined crate notice inventory.

```sh
python3 examples/tester-cd/build.py --queue-desk limine out-desk
python3 examples/tester-cd/check.py --queue-desk out-desk evidence-desk
```

At the launcher, press Down and Enter to open the desk. N opens a new request. Type a label, press Enter to save and Esc to return. Reopen the desk to read the label, then press F to finish the request. On this CD the journal is held in RAM until power-off. The graphical desk records requests locally. It can be exercised with the CD as the only attached medium.

The checker creates a request named `notes`, reopens the desk twice and checks both the active and finished states. Each time it compares the displayed label against the app’s own glyphs. The host archives include serial logs and the three queue screens. Download the optional CI artifacts ending in `-queue-desk`.

## First result

At `8244de3` plus the changes of this revision, on Linux x86_64 with QEMU 8.2.2 (TCG): kernel measurement `103f476e9532f85017ea5839f4444f73085465ce36f3d22c6e4372202148565a`, the same from differently named output directories; all four sessions passed. The image digest is in each build's receipt and is not repeated here, because it contains the commit it was built from. On a hosted runner the same recipe gave a different measurement, for the reason given above. Director B3 ran the disk check on the runner's image: no guest write to an attached disk on PC IDE, Q35 IDE and Q35 NVMe with 512 and 4,096-byte sectors ([read-back](https://github.com/KirtusJ/pcp-os/pull/291#issuecomment-7056064827)).

## What this does not show

One emulator on one host. No physical machine, no UEFI firmware (see [issue 281](https://github.com/KirtusJ/pcp-os/issues/281)), no other hypervisor, no attached disk (the [disk check](../optical-disk-check/README.md) covers the loader), and no storage that outlasts power, which the kernel does not have. The license files in `notices.txt` are the ones each crate publishes; whether that meets every license's terms for a distributed image has not been reviewed.
